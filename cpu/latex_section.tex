\section{Experimental Methodology}
\label{sec:methodology}

To evaluate the performance and energy efficiency of dedicated Intel SHA-NI (SHA New Instructions) hardware extensions and discrete GPU acceleration against a traditional software implementation, we designed a heterogeneous experimental environment using:
\begin{itemize}
    \item \textbf{CPU Node:} An Intel Core i7-1255U processor (12th Gen Alder Lake architecture) featuring 2 Performance cores (P-cores) and 8 Efficient cores (E-cores). Workloads were confined exclusively to the E-cores (running at a fixed base frequency of 3.5~GHz, without Hyper-Threading) via the Linux \texttt{taskset} utility (mapping threads to CPU IDs 4--7).
    \item \textbf{GPU Node:} An NVIDIA GeForce RTX 2050 laptop GPU (GA107M, Ampere architecture) with 2,048 CUDA cores and 4~GB of dedicated GDDR6 VRAM, operating over a PCIe bus.
\end{itemize}

We evaluated three distinct implementation paradigms for the SHA-256 algorithm:
\begin{enumerate}
    \item \textbf{CPU Software (SW):} A standard C scalar implementation compiled using GCC with the \texttt{-mno-sha} and \texttt{-march=x86-64} compiler flags to prevent the compiler from generating any hardware-accelerated instructions.
    \item \textbf{CPU Hardware-Accelerated (HW / SHA-NI):} An implementation utilizing OpenSSL 3.5.5's high-level \texttt{EVP} API, which leverages runtime CPUID dispatch to call dedicated Intel SHA-NI instructions (\texttt{SHA256RNDS2}, \texttt{SHA256MSG1}, and \texttt{SHA256MSG2}).
    \item \textbf{GPU Hardware-Accelerated (CUDA):} A parallel CUDA C/C++ kernel. The workload is partitioned into $N$ independent chunks, and a 1D grid of CUDA thread blocks is launched, assigning exactly one thread to hash each chunk. The data is transferred from host memory to device memory, executed on-chip, and the resulting hashes are copied back.
\end{enumerate}

The workload consisted of hashing a 1.0~GB binary payload. Prior to running the benchmarks, the payload was pre-warmed into the OS page cache (\texttt{dd} utility) to eliminate disk I/O latency. CPU energy consumption was gathered from the Intel RAPL package-0 interface (\texttt{/sys/class/powercap/intel-rapl:0/energy\_uj}). GPU power draw was monitored dynamically in the background at 100~ms polling intervals using the NVIDIA System Management Interface (\texttt{nvidia-smi} utility) query tool. A total of 5 runs were performed per configuration to compute the mean and standard deviation.

\subsection{Throughput and Hardware Acceleration Analysis}

As shown in Table~\ref{tab:sha256_results}, the single-threaded CPU hardware implementation (\texttt{CPU HW 1T}) leverages Intel SHA-NI to yield a throughput of 1,763.18~MB/s, representing a \textbf{9.29$\times$} speedup over the software baseline (\texttt{CPU SW 1T}). 

When offloaded to the discrete GPU, the execution throughput increases dramatically. Hashing with 256~KB chunks, the CUDA kernel achieves a compute throughput of \textbf{7,587.84~MB/s} (7.41~GB/s), which is a \textbf{39.99$\times$} speedup over the single-core CPU software baseline. This acceleration highlights the massive arithmetic density of the GPU core architecture when executing highly parallel independent hash lanes.

\subsection{PCIe Bus Overhead and End-to-End Bottlenecks}

A critical consideration in GPU acceleration is the PCIe data transfer overhead. While the raw GPU computation (Kernel Only) achieves 7,587.84~MB/s at 256~KB chunks, the End-to-End (E2E) throughput (which includes copying the 1.0~GB payload to VRAM and copying the hashes back) drops to \textbf{2,662.40~MB/s}. 

This reduction shows that the PCIe bus link is the primary bottleneck for GPU cryptographic workloads, limiting overall system throughput to about 35\% of the on-device kernel rate. Thus, GPU acceleration is highly beneficial for latency-tolerant, high-volume batch processing, but for latency-critical single-block operations, the overhead of bus transfers makes CPU SHA-NI more suitable.

\subsection{Granularity and Chunk Size Effects on GPU Performance}

The GPU performance shows a non-linear relationship with chunk size. The kernel throughput drops from 3,655.68~MB/s at 4~KB to 2,877.44~MB/s at 64~KB, before surging to \textbf{7,587.84~MB/s} at 256~KB. 

This behavior is caused by two factors:
\begin{itemize}
    \item At small chunk sizes (4--64~KB), the large number of active threads (up to 262,144 for 4~KB chunks) creates severe contention in the GPU L2 cache and registers, leading to thread scheduler scheduling overhead and cache trashing.
    \item At larger chunk sizes (256~KB), the number of active threads is reduced to 4,096. This reduction eliminates cache thrashing and allows each thread to execute long sequential read loops. These loops utilize sequential memory bursts that match the GPU's L2 cache lines perfectly, maximizing hardware utilization.
\end{itemize}

\subsection{Energy Efficiency Evaluation}

The energy efficiency (J/GB) highlights the "race-to-sleep" advantage of high-throughput accelerators. While the CPU software implementation requires 69.76~J/GB in monohilo execution, the multi-core CPU SHA-NI implementation reduces this to 5.17~J/GB. 

The GPU GPU CUDA configuration at 256~KB chunk size achieves the lowest energy cost of just \textbf{3.77~J/GB} E2E (and only \textbf{1.32~J/GB} if focusing on kernel computation). Despite drawing a higher transient power (~10.5~W for the dGPU package alone), the massive throughput reduces the overall active execution time, making the discrete GPU the most energy-efficient option for high-throughput batch workloads.
